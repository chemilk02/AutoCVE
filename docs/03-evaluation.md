# AutoCVE 평가 (M5)

MVP 범위([01-mvp-scope.md](01-mvp-scope.md) §6)의 성공 지표를 측정하고, 정답 셋으로 판정 정확도를 확인하는 방법이다.

## 1. 무엇을 재는가

| 지표 | 정의 | 목표 |
|------|------|------|
| 알림 지연 (p90) | 취약점이 OSV에 반영된 시각(`modified`) → 알림 시각. 저장소 등록 전부터 있던 취약점은 뺀다 | 2시간 이내 |
| Claude 없이 종결된 비율 | 마지막 판별이 자동 종결·dev 전용·악성·철회·버전 불일치인 후보 / 판별한 후보. 감사 표본은 뺀다 | 60% 이상 |
| 자동 종결 감사 오판율 | 감사 표본 중 Claude가 `affected`로 본 비율 | 5% 이하 |
| Opus 도달 비율 | Opus 분석을 한 번이라도 받은 후보 / 판별한 후보 | 10% 이하 |
| 사용자가 판정을 뒤집은 비율 | 처리 기록 중, 처리 직전 시스템 판정과 사용자 판단이 반대인 비율 | 15% 이하 |
| 후보 1건당 평균 LLM 비용 | 전체 비용(평가 실험 비용 제외) / 판별한 후보 | 기준선 측정 |

정답 셋이 있으면 다음도 계산한다.

- 정확도, 정밀도, 재현율
- **놓친 비율**: 정답이 "영향 있음"인데 "영향 없음"으로 판정한 비율. 가장 위험한 오류라 따로 본다.
- 자동 종결됐지만 실제로는 영향이 있던 건수
- `uncertain`(사람 검토)과 분석 전 후보는 정확도에 넣지 않고 따로 센다.

채점에는 **사용자가 처리하기 직전의 시스템 판정**을 쓴다. 처리 후에는 판정이 사용자 값으로 바뀌기 때문이다.

## 2. 정답 셋

### 2.1 사용자 처리 기록에서 만들기

Finding 상세 화면의 처리 버튼이 정답이 된다.

| 처리 | 정답 |
|------|------|
| 영향 있음 확인 | `affected` |
| 수정 완료 | `affected` |
| 해당 없음 (사유) | `not_affected` |
| 다시 열기 | 정답에서 뺀다 |

Finding마다 마지막 처리만 쓴다. 웹의 **평가** 화면은 이 기록을 정답으로 삼는다.

```bash
python -m autocve.cli eval export-feedback > cases.json
```

### 2.2 직접 작성하기

```json
{
  "cases": [
    {
      "repo_url": "https://github.com/owner/repo",
      "advisory_id": "GHSA-xxxx-xxxx-xxxx",
      "package": "lodash",
      "expected": "affected",
      "note": "src/render.js에서 사용자 입력을 _.template에 넘김"
    }
  ]
}
```

- `repo_url`은 프로젝트에 등록한 주소와 같아야 한다.
- `advisory_id`는 GHSA, CVE, PYSEC 등 별칭 중 무엇을 써도 된다.
- `package`의 PyPI 이름은 대소문자와 `-`, `_`, `.` 차이를 무시한다.
- 같은 패키지가 lockfile 여러 곳에 설치되어 있으면 그 Finding 모두를 같은 정답으로 채점한다.

## 3. 실행

```bash
# 지표 + 정확도 + 임계값 보정 (Markdown)
python -m autocve.cli eval report [--dataset cases.json]

# 자동 종결 임계값 보정. --apply는 권장값을 워크스페이스에 저장한다.
python -m autocve.cli eval calibrate [--dataset cases.json] [--apply]

# 비교 실험: 현재 파이프라인 vs Opus 단일(effort low)
python -m autocve.cli eval experiment --dataset cases.json --strategy current --strategy opus_low --yes
```

### 3.1 임계값 보정

- 정답이 있는 후보 중 **JEV가 판별한 것**만 쓴다. 규칙·캐시 판별의 값은 확률이 아니기 때문이다.
- 임계값 0.80~0.99마다 다음을 계산한다.
  - 자동 종결되었을 후보 수: "영향 없음" 확률이 임계값 이상이고, 경로가 `no_llm`이고, KEV도 CVSS 9 이상도 아닌 후보
  - 그중 실제로는 영향이 있던 비율
- 오판율 5% 이하인 임계값 중 가장 많이 종결하는 값을 권장한다.
- 표본이 20건 미만이면 권장하지 않는다. 모든 값이 기준을 넘으면 0.99를 권장한다.
- 운영 중에는 감사 표본으로도 임계값을 자동으로 올린다(아키텍처 §4.4). 이 보정은 정답 셋으로 **내리는** 것까지 할 수 있다.

### 3.2 비교 실험

아키텍처 §5.2의 질문을 확인하는 실험이다. "JEV 라우팅 캐스케이드가, 가장 좋은 모델을 낮은 effort로 한 번 쓰는 것보다 정말 싸고 정확한가?"

- `current`: 이미 DB에 있는 판정과 기록된 비용을 그대로 쓴다. **API를 부르지 않는다.**
- `opus_low`: 정답 셋의 Finding마다 저장소를 clone하고 Opus(effort low)로 심층 분석을 다시 돌린다.
  - **비용이 든다.** `--yes` 없이 실행하면 건수와 추정 상한(건당 $0.50)만 알려 주고 멈춘다.
  - 비용은 `stage="eval"`로 기록하므로 운영 지표와 섞이지 않는다.

캐스케이드는 모델이 나뉘어 프롬프트 캐시를 재사용하지 못하므로, 단일 모델이 비용 대비 나을 수도 있다. 결과에 따라 기본 라우팅을 바꾼다.

## 4. 해석할 때 주의할 점

- 사용자 처리 기록은 사용자가 처리한 후보에 치우친다. 보통 알림을 받은 위험한 후보다. 자동 종결된 후보는 사용자가 거의 보지 않으므로, 감사 표본과 직접 만든 정답 셋으로 보완한다.
- 표본이 작을 때 비율 지표는 크게 흔들린다. 리포트의 분모(건수)를 같이 본다.
- 비용은 단가표(`autocve/llm/pricing.py`)로 계산한 추정치다. Anthropic Console의 실제 청구액과 주기적으로 맞춰 본다.
