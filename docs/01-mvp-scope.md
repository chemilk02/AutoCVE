# AutoCVE MVP 범위

## 1. 한 줄 정의

> 공개 취약점 DB에 새 취약점이 올라오면, 연결된 저장소가 **실제로 영향을 받는지** 판별하고
> 근거와 위험도를 알려준다. 저비용 판별 모델 **JEV**가 먼저 위험 여부와 분석 모델을 결정하고,
> 근거 생성이 필요한 경우에만 사용자 본인의 Anthropic API 키(BYOK)로 Claude를 호출한다.

## 2. 검증하려는 가설

| # | 가설 | 측정 방법 |
|---|------|-----------|
| H1 | 버전 매칭만 하는 기존 SCA 알림의 상당수는 실제 영향이 없다 | 알림 중 최종 판정 `not_affected` 비율 |
| H2 | JEV 판별만으로 상당수 후보를 Claude 호출 없이 정리할 수 있다 | Claude 호출 없이 종결된 후보 비율과, 그중 감사 샘플의 오판율 |
| H3 | JEV 라우팅이 "항상 Opus"보다 훨씬 싸면서 판정 품질은 비슷하다 | 정답 셋 기준 정확도와 후보 1건당 비용 비교 |
| H4 | 사용자는 근거가 붙은 판정을 신뢰하고 그대로 처리한다 | 사용자가 판정을 뒤집은 비율 |

## 3. 대상 사용자

- GitHub을 쓰는 소규모 개발팀 (보안 전담 인력 없음)
- Node.js(npm) 또는 Python(PyPI) 기반 서비스

## 4. MVP 기능 (In scope)

| ID | 기능 | 설명 |
|----|------|------|
| F1 | 취약점 피드 수집 | OSV(npm, PyPI) 증분 수집 1시간 주기, EPSS·CISA KEV 1일 주기 |
| F2 | 저장소 연결 | GitHub fine-grained PAT(Contents read-only)로 저장소 등록, 일 1회 + 수동 재스캔 |
| F3 | 의존성 인벤토리 | `package-lock.json`, `poetry.lock`, `requirements.txt` 파싱 → 직접/간접, prod/dev 구분 |
| F4 | 코드 사용처 인덱스 | 파일별 import 목록과 해시. Python은 `ast`, JS/TS는 import/require 파서 |
| F5 | 양방향 매칭 | 새 취약점 → 영향받는 저장소, 새 의존성 → 기존 취약점 |
| F6 | JEV 판별 게이트 | 후보마다 위험 여부 확률과 분석 경로(`no_llm`/Haiku/Sonnet/Opus)를 결정 ([아키텍처 §4](02-architecture.md#4-판별-게이트-jev)) |
| F7 | Claude 분석 | JEV가 고른 모델로 근거 생성. Haiku는 스니펫 단위, Sonnet/Opus는 코드 탐색 도구를 쓰는 심층 분석 |
| F8 | 위험도 산정 | CVSS × 악용 가능성(EPSS/KEV) × 도달성 판정 × 노출도 → 5단계 등급과 근거 |
| F9 | 알림 | Slack Webhook, 이메일. Critical/High는 즉시, 나머지는 일일 요약 |
| F10 | 키 관리 (BYOK) | Anthropic 키(필수)와 TypeSafe 키(선택) 입력·검증·암호화 저장, 모델 선택, 월 예산 상한, 사용량 대시보드 |
| F11 | 판정 처리와 피드백 | 사용자가 `수용`, `해당 없음(사유)`, `수정 완료`로 처리. JEV 임계값 보정 데이터로 축적 |

**JEV 키가 없을 때**: 판별 게이트는 규칙 기반 점수로 대체 동작한다. 정확도는 떨어지지만 서비스는 Anthropic 키만으로 돌아간다.

## 5. MVP에서 제외 (Out of scope)

- 컨테이너 이미지, OS 패키지, C/C++ 벤더링 코드 → Phase 2
- 자동 패치 PR 생성 → Phase 2
- 멀티 테넌트 SaaS, 결제 → Phase 2. MVP는 **단일 워크스페이스 self-host**(Docker Compose). 단, 스키마에는 `workspace_id`를 처음부터 둔다.
- GitHub App, Webhook 기반 실시간 스캔 → Phase 1
- NVD 직접 연동. MVP는 OSV에 실린 심각도를 사용하고, 비어 있으면 NVD로 보강한다 (Phase 1)
- KNVD/KISA 연동, 한국어 규제 보고서 → Phase 2

## 6. 성공 지표 (MVP 종료 시점)

| 지표 | 목표 |
|------|------|
| 알림 지연: OSV 반영 → 알림 | 2시간 이내 |
| Claude 호출 없이 종결된 후보 비율 | 60% 이상 |
| JEV 자동 종결 건의 감사 샘플 오판율 | 5% 이하 (Critical/KEV는 자동 종결 대상에서 제외) |
| Opus 도달 비율 | 후보의 10% 이하 |
| 사용자가 판정을 뒤집은 비율 | 15% 이하 |

**비용 추정** (공개 단가 기준이며, 실측값으로 바꿀 추정치)

| 단계 | 모델 | 단가 (입력 / 출력, per MTok) | 가정 | 1건당 |
|------|------|------------------------------|------|-------|
| 판별 | JEV | $0.042 / 출력 없음 | 입력 4K | 약 $0.0002 |
| 경량 분석 | `claude-haiku-5-5` | $0.10 / $0.50 | 입력 3K, 출력 400 | 약 $0.0005 |
| 중간 분석 | `claude-sonnet-5-5` | $2 / $10 | 누적 입력 40K, 출력 3K | 약 $0.11 |
| 심층 분석 | `claude-opus-5-5` | $4 / $20 | 누적 입력 100K, 출력 5K | 약 $0.50 |

모든 후보에 JEV를 돌려도 비용은 거의 0에 가깝습니다. 전체 비용은 **Sonnet/Opus로 라우팅되는 비율**이 결정합니다.

JEV 단가와 벤치마크 수치는 대부분 벤더 측 자료입니다. M5에서 직접 측정해 대체합니다.

## 8. 열린 질문

1. **TypeSafe 키도 사용자가 입력하는가?** 이 문서는 Anthropic 키와 같은 BYOK(선택 입력)로 가정했다. 서비스 운영자 키로 JEV 비용을 부담하는 방식도 가능하다.
2. **JEV API 세부 사항 확인**: 엔드포인트, 요청 필드, 버전 고정 방법은 서드파티 자료로만 확인한 상태다. 구현 전에 공식 문서로 검증한다 ([아키텍처 §4.6](02-architecture.md#46-검증이-필요한-jev-사항)).
3. **배포 형태**: self-host로 시작하는 게 맞는가, 처음부터 SaaS로 가는가? 코드 스니펫이 Anthropic과 TypeSafe로 전송되므로, SaaS라면 고지와 동의 절차가 필요하다.
4. **대상 생태계**: npm + PyPI로 충분한가? (Maven, Go 추가 여부)
